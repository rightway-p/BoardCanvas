# Signed updater releases

BoardCanvas uses its signed release manifest and the external recovery helper for Windows current-user NSIS updates. The beta rollout is the default. Beta and stable binaries accept only their own signed channel; promotion from beta to stable is a separate, explicit action in Settings → App info.

## Repository setup

Configure these GitHub Actions secrets before dispatching `Signed Windows release`:

- `TAURI_PRIVATE_KEY`: encrypted Tauri 1 updater private key contents.
- `TAURI_KEY_PASSWORD`: password for that key.
- `TAURI_UPDATER_PUBLIC_KEY`: exact contents of `src-tauri/updater.pub`.

The workflow compares the configured public key with the checked-in key and fails closed if any secret is absent. Keep the private key and its password outside the repository. On Windows, the local test builder reads the password from a current-user DPAPI-protected file. `BOARD_RELEASE_CHANNEL` and `BOARD_RELEASE_VERSION` are set for every build; local version overrides use temporary Tauri config files and never rewrite tracked package files.

Create the GitHub `board-beta` prerelease once before the first beta feed update. Configure the `stable-release` GitHub environment with required reviewers; its approval is the stable release gate. The workflow only runs by manual dispatch, requires the already-existing immutable `v<version>` tag, and never creates or pushes Git tags.

A fresh local Windows `npm run desktop:build` or `npm run desktop:dev` requires the recovery helper to be built and staged first:

```powershell
cargo build --manifest-path src-tauri/Cargo.toml --bin boardcanvas-recovery --features recovery-helper-build --release
New-Item -ItemType Directory -Force src-tauri/resources
Copy-Item -LiteralPath src-tauri/target/release/boardcanvas-recovery.exe -Destination src-tauri/resources/boardcanvas-recovery.exe -Force
```

## Beta rollout

Dispatch the workflow at an immutable beta tag such as `v2.0.1-beta.2`, with channel `beta`. It builds with `BOARD_RELEASE_CHANNEL=beta`, signs the NSIS installer and `board-release.json`, creates the versioned beta release, and updates only `board-release.json` plus its signature on the rolling `board-beta` prerelease. The signed manifest points to the immutable installer at `releases/download/v<version>/...`.

The local builder creates a signed two-version fixture feed for update and rollback exercises. Build the helper and both local beta installers with:

```powershell
./scripts/build-local-recovery-feed.ps1 -FeedRoot ./tmp/local-signed-update-test/2026-10-06
```

Choose a new fixture directory for each run; existing directories are never overwritten. The fixture root contains `board-release.json` and `.sig` for the update check, plus a `v<version>` directory for each signed installer and its version-specific metadata. Set `BOARD_RECOVERY_TEST_FEED` to that absolute root only in the test app's process environment. The `recovery-test-feed` feature is used only by this local builder and is excluded from the release workflow.

After BoardCanvas initializes the recovery component, its verified helper copy is stored outside the install folder at `%LOCALAPPDATA%\com.rightway.boardcanvas-recovery\boardcanvas-recovery-<sha256>.exe`. Running the helper without arguments opens its user-confirmed recovery menu; `--status` only reads the journal. It never performs rollback or interrupted recovery automatically from a direct launch.

## Stable promotion

After beta and hardware validation, add a reviewed record at `docs/release-validation/<version>.md` on the immutable stable tag. It must contain these exact fields:

```text
status: reviewed
beta_validation: passed
hardware_validation: passed
reviewer: <named reviewer>
```

Dispatch that tag with channel `stable` and approve the protected `stable-release` environment, whose required reviewers are the enforceable release gate. The checked-in record is an additional fail-closed validation requirement; an arbitrary URL or workflow boolean is not sufficient. The job compiles a separate `BOARD_RELEASE_CHANNEL=stable` binary and publishes the signed manifest as the latest stable feed. Stable artifacts are not generated by the beta workflow.
