# 업데이트 및 직전 버전 복구 설계

상태: 구현 전 제안. 이 문서는 사용자가 이미 지정한 요구, 구현 기본안, 배포 결정 대기, 미구현 항목을 구분한다. 제안된 배포 방식이나 세부 동작은 사용자 결정으로 간주하지 않는다.

## 사용자 요구

- 업데이트 설치를 사용자가 선택하고, 설치 전 취소할 수 있어야 한다. 취소 뒤에도 메뉴에서 다시 확인할 수 있어야 한다.
- 업데이트 설치 후 문제가 생기면 **직전 설치 버전**으로 돌아갈 수 있어야 한다. 설치 전 취소와 별개의 복구다.
- 업데이트 설치 전 작업 캐시 저장이 성공해야 한다. 다운로드나 설치 실패 뒤 기존 버전을 사용할 수 있어야 한다.
- 업데이트·복구 과정에서 작업 파일, 필기, 사용자 데이터를 보존해야 한다.

## 현재 상태와 제한

- `src-tauri/tauri.conf.json`: 패키지 버전은 `2.0.1`; 번들 생성은 `active: false`.
- `src-tauri/Cargo.toml`: Tauri 의존성에 `updater` feature가 없다.
- `src-tauri/src/commands/drive.rs`: `get_updater_status`는 활성화, HTTPS endpoint, 비어 있지 않은 공개키가 모두 있을 때만 설정 완료를 보고한다.
- `js/board-2.0.1-ui.js`: 설치 전 `persistSessionState()`를 호출한 뒤 Tauri updater 설치 함수를 부른다. 이는 현재 웹 저장소의 저장 경로이며 설치본, WebView 프로필, 사용자 파일 전체가 롤백 뒤에도 보존됨을 증명하지 않는다.
- 2026-10-05 확인: `rightway-p/BoardCanvas` GitHub Releases 목록이 비어 있다. 따라서 현재 저장소에서 내려받을 실제 직전 서명 설치본이 확인되지 않았으며, 설치·롤백을 제공하거나 검증할 수 없다.

## 제안 기본안 — 검증과 승인 전

1. 첫 대상은 Windows per-user NSIS 설치로 한정해 signed Tauri updater를 연결한다. GitHub Releases와 HTTPS manifest는 후보 경로일 뿐이며 배포 위치는 미정이다. 다른 설치 방식과 플랫폼은 별도 검증 전 지원을 약속하지 않는다.
2. 정상 업데이트는 현재 앱보다 새 버전만 제안한다. 직전 버전 복구는 별도의 명시적 명령으로 실행하며, 현재 설치본의 기록에 고정된 **직전 성공 설치본**만 대상으로 한다. 기록에는 앱 identity (`com.rightway.boardcanvas`), 버전, OS/architecture, per-user NSIS 설치 종류, 서명된 package의 artifact digest, 설치된 실행 파일의 fingerprint를 서로 다른 필드로 둔다. 설치 전에는 package 서명과 package digest를 대조한다. 설치 후에는 배포가 제공하는 신뢰 가능한 post-install probe로 identity/version을 확인하거나 기대 실행 파일 fingerprint를 검증한다. 서로 다른 앱/플랫폼/설치 종류, 또는 일치하지 않는 package digest/fingerprint는 거부한다. 전역 최신 릴리스의 이전 항목을 추측해 되돌리지 않는다.
3. 현재 앱 설치 폴더 교체·부분 삭제와 무관하게 실행 가능한, 설치 앱 밖의 안정 경로에 최소 Windows 복구 실행 파일을 둔다. 시작 메뉴 진입점은 이 도구를 실행한다. journal, checkpoint, 복구 artifact도 정해진 안정 경로에 두고, 기록된 앱 identity와 데이터 경로가 실제 설치와 일치하는지 및 앱/WebView 프로필이 닫혀 잠금 해제됐는지 검증한다. 경로가 예상 위치 밖을 가리키거나 프로필 잠금을 확인할 수 없으면 변경을 중단한다. 도구는 대상의 identity·플랫폼·설치 종류·서명·digest를 확인한 뒤 설치한다.
4. 앱을 닫은 상태에서 네이티브 도구가 작업·설정과 필요한 WebView 프로필 데이터를 확인된 경로에서 복구 체크포인트로 기록한다. JS autosave 성공만으로 이 단계를 대체하지 않는다. 설치 전 checkpoint, 안정 경로, app-data 경로 및 위 설치 메타데이터를 원자적이고 검증 가능한 형태로 준비한다.
5. 복구 시 현재 작업 데이터와 설정도 먼저 별도로 보존한다. 이전 체크포인트를 현재 데이터 위에 무조건 덮어쓰지 않는다. 현재 상태를 보존한 다음, 이전 버전에서 읽을 수 있는지 확인된 데이터만 복원한다.
6. 지원할 데이터 스키마는 이전 버전에서 읽을 수 있도록 유지하거나 무손실 변환을 검증한다. 보존을 보장할 수 없는 스키마라면 설치 전 또는 복구 전환 전에 차단하고 데이터 보관 위치와 조치를 안내한다. 데이터 손실을 감수하는 롤백을 성공으로 보고하지 않는다.
7. 업데이트/복구 journal 상태는 `ready → prepared → installing → needs-verification → confirmed` 또는 `failed`로 둔다. 새 이전 버전 기록은 고정 package 검증 기록과 실제 대상 실행 파일의 identity·버전·별도 fingerprint를 확인하고 재실행에 성공한 뒤에만 교체한다. 동시에 두 설치/복구 작업은 허용하지 않는다.
8. 업데이트 설치 뒤 실제 실행 파일의 identity·버전을 신뢰 가능한 post-install probe로 확인하거나 별도 실행 파일 fingerprint를 검증하기 전에는 성공으로 표시하지 않고 journal을 `needs-verification`으로 유지한다. 설치 패키지 digest를 실행 파일 지문으로 사용하지 않는다. probe/fingerprint의 신뢰 가능한 출처와 검증 방식은 구현 전 확정하고, 확인 전까지 성공 처리하지 않는다. 설치 프로그램 시작 뒤 실패나 강제 종료가 일어나도 현재 버전이 안전하다고 간주하지 않는다. 앱 재실행 또는 외부 복구 진입점에서 실제 설치 상태를 판별하고, 부분 설치라면 이전 검증 설치본과 보존 데이터를 복구한다. 중단 시 다음 실행에서 journal을 확인해 검증/복구를 재개한다. 설치 프로그램 시작 뒤 취소가 원자적이라는 약속은 실제 검증 전에는 하지 않는다.
9. 자동 업데이트 억제 기록은 복구된 버전 전체가 아니라 실패한 특정 대상 version/artifact에 한정한다. 일반 최신 버전 확인과 메뉴의 수동 확인은 유지하며, 실패 대상을 다시 설치하는 것은 사용자가 해당 재시도를 승인할 때만 허용한다. 일반 업데이트 경로에 무조건 허용하는 version comparator를 넣지 않는다. Tauri의 명시적 comparator override가 필요하다면 고정된 복구 대상에만 적용하고 정상 feed에서 다운그레이드가 차단되는 테스트를 둔다.
10. 최초 신규 설치에는 이전 설치본이 없으므로 복구는 제공되지 않는다. 기존 v1의 직접 실행 파일/portable 여부와 실제 설치 형태는 확인 중이므로 NSIS 설치로 바꾸는 것만으로 그 파일을 복구 가능한 기준 설치본으로 보지 않는다. 전환 전 기존 실행 파일의 fingerprint, archive/installer로 복원 가능한지, 설치 경로·버전·데이터 호환성을 확인하고 복구를 실시험해야 한다. 이 조건을 만족하지 못하면 기존 설치본을 교체하는 지원 업데이트를 차단한다. v1에서 새 설치 방식으로 전환하는 bootstrap 경로는 사용자 결정과 실제 설치 형태 확인 전까지 미정이며, 보존 요구를 우회하는 전환으로 가정하지 않는다. 확인되지 않은 v1을 기준 버전으로 꾸며내지 않는다.

## 미정 및 외부 의존성

- 배포 endpoint/호스팅 위치, artifact 게시 절차, 공개키와 서명키 관리 주체, 실제 이전 signed installer의 가용성, 설치된 실행 파일 fingerprint의 신뢰 가능한 출처 및 검증 방식.
- 복구 UI의 앱 내 위치와 오류 안내 문구. 외부 복구 진입점은 앱이 실행되지 않을 때 필요하다는 이유의 설계 제안이다.
- 지원 플랫폼·설치 종류 및 서명 인증서 운영. admin 권한, quiet 설치, 설치 중 취소/원자성은 실제 환경에서 확인 전 보장하지 않는다.
- 구버전이 읽을 수 있는 작업·설정/WebView 데이터 스키마의 범위와 데이터 보존 기간.
- 과거 모든 버전 복구는 요구사항이 아니다. 대상 버전의 설치본과 데이터 호환성을 검증하지 않고 v1 복구를 약속하지 않는다.

## 완료 전 필수 수용 기준

- 설치 전 취소는 현재 설치본과 데이터에 변경을 남기지 않고, 메뉴에서 재확인이 가능하다.
- 서명 불일치/변조, 오프라인, 다운로드 실패, 디스크 공간 부족은 설치를 시작하지 않거나 현재 설치본을 사용할 수 있는 실패로 남긴다.
- 체크포인트 저장 실패 시 설치를 막고 원인을 알린다. 프로세스 종료/전원 중단을 준비·설치·검증 각 단계에서 시험한다.
- 앱이 시작되지 않고 설치 폴더가 교체되거나 일부 삭제되어도 안정 경로의 복구 도구가 journal/checkpoint/artifact와 직전의 검증 설치본을 찾는다. 다른 identity, OS/architecture, 설치 종류 또는 digest가 다른 artifact는 설치하지 않는다.
- 업데이트 뒤 새 작업을 편집한 다음 롤백해도 그 편집 내용과 이전 작업·필기·사용자 데이터가 각각 보존된다. 복원할 데이터가 구버전에서 읽히지 않으면 전환을 막고 두 데이터 사본을 보존한다.
- rollback 설치 뒤 실제 실행 파일 버전과 재시작을 확인하고 성공 처리한다. 부분 설치나 강제 종료 시에도 `needs-verification`을 유지하고 외부 도구로 이전 검증본과 보존 데이터를 복구한다. 잘못되거나 서명되지 않은 artifact는 설치하지 않는다.
- 정상 업데이트 확인은 최신 버전 제안으로 동작하며 이전 버전으로 조용히 강등하지 않는다. 실패한 특정 version/artifact만 자동 재제안을 억제하고, 최신 버전 확인과 메뉴 확인은 유지한다. 해당 실패 artifact 재시도는 사용자 승인을 요구한다.
- 복구 기준이 없거나 v1 설치 형태·데이터 호환성을 확인할 수 없는 경우 기존 설치본을 교체하는 업데이트를 차단한다. 신규 설치만 기준 버전 없이 진행할 수 있다.
- 실제 Windows per-user NSIS 설치/다운그레이드에서 앱 identity `com.rightway.boardcanvas`, 기존 사용자 식별자, 기존 app-data 및 WebView 프로필 경로 재사용 여부를 확인한다. 이 identity와 경로를 임의로 바꾸지 않는다. Tauri 설정의 `allowDowngrades` 기본값만으로 설치 동작을 추정하지 않는다.

## 구현 순서 제안

1. 배포 주체가 endpoint와 키 운영을 정하고, 두 개 이상의 실제 서명 설치본 및 지원 대상 Windows 설치 방식을 준비한다. 비밀키를 저장소에 넣지 않는다.
2. Rust 복구 모듈에서 서명 확인, 버전·설치 기록, checkpoint/journal, 용량·호환성 검사와 중복 실행 차단을 구현한다.
3. 앱 바깥 복구 실행점과 설치 완료 후 버전 확인 경로를 연결한다. 앱 설정 UI에는 상태, 명시적 복구, 일반 업데이트 재시도를 최소한으로 노출한다.
4. 아래 수용 기준을 실 설치본으로 검증한다. 실패나 미실행 항목이 있으면 배포/리뷰 완료로 처리하지 않는다.
5. 의미 있는 구현 단위 뒤 현재 diff의 단순성을 점검하고, 독립 Codex 및 Antigravity 리뷰를 모두 수행한다. actionable finding을 처리하고 false positive/보류 사유와 리뷰어·실행 주체를 기록한다.

현재 작업은 이 설계 문서 작성에 한정한다. 기능 활성화, 키 생성/게시, 사용자 데이터 변경, 배포, 리뷰 완료 선언은 포함하지 않는다.
